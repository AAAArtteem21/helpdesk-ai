# Helpdesk AI Drafts

Сервіс приймає звернення з хелпдеска (вебхук), знаходить релевантні статті бази знань, генерує чернетку відповіді через LLM. Оператор у веб-інтерфейсі підтверджує або відхиляє чернетку, після чого відповідь надсилається клієнту через API хелпдеска.

## Швидкий старт

```bash
git clone <repo> && cd helpdesk-ai
docker compose up --build
```

- Інтерфейс оператора: http://localhost:8000
- Вебхук: `POST http://localhost:8000/webhooks/helpdesk`
- Мок хелпдеска: http://localhost:9000

`.env` не обов'язковий (є дефолти); для зміни налаштувань: `cp .env.example .env`.

Без `LLM_API_KEY` сервіс працює в режимі без ключа (див. нижче).

### 2. Перевірка вебхука та генерації відповіді через LLM

Команда створює тестове звернення українською мовою. Worker знаходить відповідну статтю бази знань, генерує чернетку відповіді та зберігає її в системі.

```powershell
$body = @{
    event_id = "render-test-003"
    ticket_id = "RENDER-003"
    customer_email = "test@example.com"
    message = "Я забув пароль. Як відновити доступ до облікового запису? Скільки часу дійсне посилання для скидання пароля?"
    reply_url = "http://127.0.0.1:9000/tickets/RENDER-003/replies"
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "https://helpdesk-ai-10bg.onrender.com/webhooks/helpdesk" `
    -Method POST `
    -ContentType "application/json" `
    -Body $body
```

Очікувана відповідь вебхука: `accepted`.

Після виконання команди:

1. Відкрийте https://helpdesk-ai-10bg.onrender.com/
2. Знайдіть звернення `RENDER-003`.
3. Переконайтеся, що згенеровано чернетку відповіді.
4. Перевірте джерело `KB-3` (стаття про скидання пароля).
5. Натисніть **Approve** або **Reject**.

`reply_url` вказує на Mock Helpdesk, запущений у тому самому Render-контейнері. Тому використовується `127.0.0.1:9000`, а не локальна адреса вашого комп'ютера.

## Ендпоінти

- `GET /health` -> 200 `OK`
- `POST /webhooks/helpdesk` -> приймає звернення, відповідає 200 одразу (новий: `accepted`, дубль: `duplicate`)
- `GET /` -> список звернень з фільтром за статусом
- `GET /tickets/<id>` -> звернення, чернетка, джерела; Approve / Reject
- `GET /kb/<slug>` -> стаття бази знань (на неї посилається чернетка)
- `GET /api/stats` -> службовий, лише при `ENABLE_SIM_API=1`, для `simulate.py`

Формат вебхука:

```json
{
  "event_id": "...",
  "ticket_id": "...",
  "customer_email": "...",
  "message": "...",
  "reply_url": "..."
}
```

## Життєвий цикл звернення

```text
received -> drafting -> draft_ready -> approved -> sending -> sent
                                |                          |
                                +-> rejected               +-> failed
```

`failed` також можливий зі стану `drafting` (вичерпано спроби генерації).

## Архітектура і рішення

- **Вебхук** лише записує в БД і відповідає 200, LLM у запиті не викликається (ліміт 2 с).

- **Дублікати**: `event_id` унікальний; паралельні дублікати відсікає constraint у БД, а не перевірка в коді. Дубль теж отримує 200, щоб хелпдеск не ретраїв.

- **Черга в Postgres**, без Celery/Redis: менше рухомих частин. Воркер бере рядки через `SELECT ... FOR UPDATE SKIP LOCKED` і виставляє lease (`locked_until`). Якщо воркер впав, тікет підхоплюється після спливу lease, тому звернення не губляться.

- **Fencing**: результат записується лише якщо `status` і номер спроби (`attempts`) не змінилися. Запізнілий воркер, чий тікет уже перехопив інший, нічого не перезапише.

- **Пріоритет**: нові звернення йдуть раніше за повторні спроби (`ORDER BY (attempts > 0), next_attempt_at`).

- **Approve/Reject** це умовний `UPDATE ... WHERE status='draft_ready'`: подвійний клік чи гонка двох операторів не можуть надіслати відповідь двічі. Текст і статус змінюються одним запитом.

- **База знань**: Postgres FTS (конфіг `simple`) з префіксними основами слів, бо в Postgres немає українського словника. Ембедінги не використовуються, щоб усе працювало без API-ключа. У промпт іде топ-3 статті, у відповіді стоять посилання `[KB-id]`, а id використаних статей зберігаються в тікеті.

### LLM: ліміти і режим без ключа

Пік 500 звернень за 10 хвилин — це приблизно 50 викликів на хвилину при ліміті 60. При затримці 5–30 с одночасних викликів близько 15–25, ліміт одночасності 30 (семафор).

Лімітер — це **ковзне вікно**, а не token bucket: ліміт провайдера заданий як N за будь-яку хвилину, а token bucket ємністю 60 може дати до приблизно 120 запитів за хвилину.

429 призупиняє всі виклики на `Retry-After` і не рахується як спроба генерації.

Без `LLM_API_KEY`: запит до провайдера все одно надсилається (займає слот ліміту), відповідь ігнорується, чекаємо `uniform(5, 30)` с і віддаємо статичну чернетку тим самим шляхом і в тому самому форматі, що й справжню.

### Доставка клієнту: at-least-once + Idempotency-Key

Строго exactly-once без підтримки дедуплікації на боці хелпдеска неможливий: після таймауту ми не знаємо, чи прийняв він відповідь і лише не встиг підтвердити.

Тому ми гарантуємо, що відповідь не загубиться (ретраї з backoff, lease, відновлення після падіння воркера), а дубль відсікається на боці хелпдеска за заголовком `Idempotency-Key`.

Ключ (`reply_key`, UUID) створюється разом із тікетом і однаковий для всіх спроб відправки.

Ретраїмо: 5xx, 408, 429 (з `Retry-After`), таймаут, мережеві помилки. Інші 4xx — це `failed`.

Якщо спроби вичерпано, тікет стає `failed` з поміткою «результат невідомий», бо ми чесно не знаємо, чи дійшла відповідь. Якщо воркер помре між відправкою і записом `sent`, тікет підхопиться після lease і піде ще раз з тим самим ключем.

## Симуляція навантаження і дублів

```bash
python simulate.py --count 60 --duration 60
python simulate.py --count 200 --duration 30
python simulate.py
```

Остання команда запускає 500 звернень за 10 хвилин.

Потрібен `ENABLE_SIM_API=1` і порожній `LLM_API_KEY`.

Сценарії:

- **A**: один `event_id` 5 разів поспіль: один `accepted`, чотири `duplicate`.
- **B**: один `event_id` одночасно з 30 потоків: рівно один `accepted`.
- **D**: 10 паралельних Approve одного тікета: жодної 5xx, доставка одна.
- **C**: навантаження, час відповіді вебхука (p95 < 2 с), оператор-імітатор через UI.
- **E**: жодне звернення не втрачено, нічого не в `failed`, жодна відповідь не доставлена двічі (звірка з `GET /deliveries` мока).

### Результат контрольного навантажувального тесту

```text
A. sequential duplicates
  [PASS] all 200
  [PASS] 1 accepted, 4 duplicate

B. 30 parallel identical event_id
  [PASS] all 200
  [PASS] exactly 1 accepted

D. 10 parallel approves of one ticket
  [PASS] D: ticket got a draft
  [PASS] D: double click never gives 5xx

C. load: 500 tickets over 600s
  [PASS] all webhooks accepted bad=0
  [PASS] webhook p95 < 2s

E. waiting for processing to finish
  [PASS] no tickets lost 503/503
  [PASS] everything reached a final state
  [PASS] no ticket ended in 'failed'
  [PASS] no ticket delivered twice to the customer
  [PASS] every 'sent' ticket really was delivered

13/13 checks passed
```

Контрольний прогін з `MOCK_DEDUP=0` (хелпдеск не дедуплікує): перевірка «не доставлено двічі» падає, тобто захист тримається саме на `Idempotency-Key`.

Перевірка падіння воркера: `WORKER_LEASE_SECONDS=30`, під час симуляції:

```bash
docker compose kill worker
docker compose up -d worker
```

Через 30 секунд воркер підхоплює незавершені звернення.

## Мок хелпдеска

`mock-helpdesk` (порт 9000):

- `POST /tickets/{id}/replies` -> 201 (повтор з тим самим ключем -> 200).
- Випадково віддає 503 (`MOCK_FAIL_RATE`) і приймає відповідь, але відповідає довше за таймаут (`MOCK_SLOW_RATE`).
- `GET /deliveries` показує, що реально доставлено.
- `POST /reset` очищає стан (службовий, не публікувати назовні).

## Безпека

Текст клієнта передається в LLM як дані (обрамлений `<<< >>>`, system-промпт забороняє виконувати інструкції з нього).

У відповіді залишаються лише посилання `[KB-id]` на статті, які були передані моделі.

Інтерфейс захищений CSRF, текст клієнта екранується шаблонами.

## Відомі обмеження

- UI оператора й вебхук без автентифікації (у проді: логін та HMAC-підпис вебхука).
- `reply_url` береться з вебхука без перевірки (у проді потрібен allowlist хостів, інакше SSRF).
- Лімітер LLM працює в межах одного процесу воркера; для кількох реплік його стан треба винести в спільне сховище.
- Пошук по базі знань без морфології: префіксні основи слів, не ембедінги.
- Тікети в `failed` видно в UI, але кнопки «повторити» немає.
- `GET /api/stats` і мок хелпдеска службові, на публічному деплої мають бути вимкнені/закриті.

## Як використовувався AI

Архітектуру, схему станів, запобігання дублям і код писались у діалозі з Claude; рішення і компроміси перевірялись вручну, а кожна інваріанта покрита тестом (`python manage.py test`).

Помилки (опечатки, розбіжності моделі й міграцій, баги в `claim`) знаходили тести.

Правила для AI-агента в `CLAUDE.md`, текст завдання в `docs/TASK.md`, промпт для статей бази знань у `docs/kb-prompt.md`.
