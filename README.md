# Helpdesk AI Drafts

Сервіс приймає звернення з хелпдеска (вебхук), знаходить релевантні статті бази
знань, генерує чернетку відповіді через LLM. Оператор у веб-інтерфейсі підтверджує
або відхиляє чернетку, після чого відповідь надсилається клієнту через API хелпдеска.

## Швидкий старт

    git clone <repo> && cd helpdesk-ai
    docker compose up --build

Сервіс буде на http://localhost:8000. `.env` не обов'язковий (є дефолти);
для зміни налаштувань: `cp .env.example .env`.

## Змінні оточення

| Змінна | За замовчуванням | Опис |
|---|---|---|
| SECRET_KEY | dev-insecure-key | Django secret |
| DEBUG | 0 | режим налагодження |
| POSTGRES_* | helpdesk | доступ до БД |
| PUBLIC_BASE_URL | http://localhost:8000 | база для посилань на статті |
| LLM_API_KEY | порожньо | порожній = режим без ключа (статична відповідь із затримкою 5–30 с) |
| LLM_BASE_URL / LLM_MODEL | Groq / llama | OpenAI-сумісний провайдер |

## Ендпоінти

- `GET /health` -> 200 `OK`
- `POST /webhooks/helpdesk` -> приймає звернення, відповідає 200 одразу
- `GET /kb/<slug>` -> стаття бази знань (на неї посилається чернетка)

## Тести

    docker compose up -d db
    docker compose run --rm web python manage.py test

## Архітектура і рішення

- **Вебхук** лише записує в БД і відповідає 200, LLM у запиті не викликається (ліміт 2 с).
- **Дублікати**: `event_id` унікальний; паралельні дублікати відсікає constraint у БД.
- **Черга в Postgres** (`FOR UPDATE SKIP LOCKED` + lease), без Celery/Redis: менше
  рухомих частин, звернення не губляться після падіння воркера.
- **База знань**: Postgres FTS (`simple`) + префіксні основи слів, бо в Postgres немає
  українського словника. Ембедінги не використовуються, щоб працювати без API-ключа.
- **Відправка клієнту**: at-least-once + `Idempotency-Key` (один `reply_key` на всі
  ретраї). Строго exactly-once неможливий, якщо хелпдеск не підтримує дедуплікацію:
  після таймауту результат невідомий.

## Симуляція навантаження і дублів

    python simulate.py --count 60 --duration 60   # швидкий прогін
    python simulate.py                            # 500 звернень за 10 хвилин

навантаження, час відповіді вебхука (p95 < 2 с), що жодне звернення не втрачено
і жодна відповідь не доставлена клієнту двічі (звіряється з `GET /deliveries` мока).

## Мок хелпдеска

`mock-helpdesk` (порт 9000): `POST /tickets/{id}/replies` -> 201 (повтор з тим самим
ключем -> 200). Випадково віддає 503 (`MOCK_FAIL_RATE`) і приймає відповідь, але
відповідає довше за таймаут (`MOCK_SLOW_RATE`). `GET /deliveries` показує, що
реально доставлено; `POST /reset` очищає стан.

## Обмеження LLM і навантаження

Пік 500 звернень за 10 хвилин це ~50 викликів на хвилину при ліміті 60.
Паралельних викликів при затримці 5–30 с близько 15–25, ліміт одночасності 30.
Лімітер це ковзне вікно (не token bucket): ліміт провайдера заданий як N за хвилину,
а не як середня швидкість. 429 призупиняє всі виклики на `Retry-After`;
нові звернення мають пріоритет над повторними спробами. Лімітер працює в межах
одного процесу воркера; для кількох реплік його стан треба винести в спільне сховище.

## Безпека

Текст клієнта передається в LLM як дані (обрамлений `<<< >>>`, system-промпт
забороняє виконувати інструкції з нього). У відповіді залишаються лише посилання
`[KB-id]` на статті, які були передані моделі.

## Відомі обмеження

- UI оператора й вебхук без автентифікації (у проді: логін та HMAC-підпис вебхука).
- `reply_url` береться з вебхука без перевірки (у проді потрібен allowlist хостів, інакше SSRF).
- Лімітер LLM не розподілений між репліками воркера.
- Пошук по базі знань без морфології: префіксні основи слів, не ембедінги.

## Як використовувався AI

Архітектуру, схему станів, запобігання дублям і код писались у діалозі з Claude;
рішення і компроміси перевірені вручну, кожна інваріанта покрита тестом
(`python manage.py test`). Статті бази знань згенеровані через AI
(промпт у `docs/kb-prompt.md`).
